# ADK 1.x와 2.x의 설계 비교 — 에이전트에서 노드로, 대화 기록에서 실행 저널로

> 대상: ADK Python **v1.26.0**(태그 `427a983b`) ↔ **v2.14.0**(`main` @ `1cb926d`)
> 근거: 양쪽 소스의 클래스 계층·패키지 구성 직접 확인 + v2.0.0 릴리스 노트 +
> 저장소 안 가이드(`docs/guides/workflow/workflow`, `docs/guides/workflow/graph`, `docs/guides/apps/resumability`).
> 작성: 2026-11-09. 부품 단위 차이는 [문서 격차 점검](../migration/문서격차점검_v1.26.0_v2.14.0.md)에 있다.
> 이 문서는 그 위에서 **설계 개념이 어떻게 바뀌었고 왜 그런지**를 다룬다.

---

## 0. 한 줄 요약

**실행의 기본 단위가 "에이전트"에서 "노드"로 바뀌었고, 그 결과 세션 로그의 의미가 "대화 기록"에서
"실행 저널"로 바뀌었다.** 그래프 문법은 눈에 보이는 쪽이고, 실제로 깊은 변화는 저널 쪽이다.
LLM 호출 루프는 버리지 않았다 — 그 위에 오케스트레이션 층을 얹었다.

---

## 1. 구조적 사실 — 에이전트가 노드가 됐다

| | v1.26.0 | v2.14.0 |
|---|---|---|
| `BaseAgent` 선언 | `class BaseAgent(BaseModel)` | **`class BaseAgent(BaseNode, abc.ABC)`** |
| `src/google/adk/workflow/` | 없음 (404) | `_base_node`, `_workflow`, `_function_node`, `_join_node`, `_tool_node`, `_llm_agent_wrapper`, `_dynamic_node_scheduler`, `_node_runner`, `_node_state`, `_node_status`, `_trigger`, `_retry_config`, `_parallel_worker` |
| 그래프가 필요할 때 | `agents/langgraph_agent.py` — LangGraph를 에이전트로 감쌈 | 네이티브 `Workflow(BaseNode)` (`LangGraphAgent`는 2.14.0에도 남아 있음) |
| `events/` 패키지 | 3파일 (`event.py`, `event_actions.py`) | 14파일 (`_abort_events`, `_interrupts`, `_isolation_scope`, `_node_path_builder`, `_branch_path`, …) |

`LlmAgent`·`SequentialAgent`·`ParallelAgent`·`LoopAgent`는 모두 `BaseAgent`를 거쳐 `BaseNode`가 됐다.
`LlmAgent`는 사라진 것이 아니라 **함수·툴·`Workflow`와 같은 자격의 노드로 재배치**됐다.
`Workflow`도 노드라서 `Runner`에 에이전트처럼 넘길 수 있고 중첩할 수도 있다.

**LLM 루프는 그대로다.** `flows/llm_flows`가 여전히 `LlmAgent`를 구동한다(요청 프로세서 12 + 3개,
응답 2개). 그래서 1.x 모듈 경로가 shim으로 대부분 살아 있는 **진화형 변경**이 됐다.

## 2. 설계·개념 차이

| 축 | 1.x | 2.x |
|---|---|---|
| **제어 흐름의 주인** | 양극단 — LLM이 결정(`transfer_to_agent`: 유연하지만 비결정적·검증 불가) 또는 고정 합성(`Sequential`/`Parallel`/`Loop`: 결정적이지만 조건 분기·합류 불가) | **선언된 데이터** — 조건·병렬·합류·순환을 edge 목록으로 선언. 인스턴스화 시점에 10개 규칙으로 컴파일·검증. LLM은 판단이 필요한 노드에만 |
| **합성 방식** | 에이전트 트리 + 공유 히스토리. 데이터는 세션 state나 대화 텍스트로 전달 | **데이터플로** — 노드 출력이 다음 노드의 `node_input`. 들어오는 노드가 모두 끝나면 스케줄, 서로 의존하지 않는 가지는 자동 병렬 |
| **대화와 계산** | 구분 없음 — 모든 에이전트가 대화 참여자 | `LlmAgent.mode`로 분리 — `chat`(전송으로 도달), `task`(사용자와 대화하며 과업 수행), `single_turn`(대화 없이 완료, **워크플로 노드의 기본값**) |
| **이벤트의 의미** | 대화 히스토리 = LLM contents의 재료 | **실행 기록** — `node_info.path`(어느 노드), `output`/`output_for`(데이터), `isolation_scope`(가시성), 체크포인트, 인터럽트, 중단 봉인 |
| **시간 축** | invocation = 요청-응답 루프 한 번 | 며칠에 걸친 실행 — 체크포인트로 재개, 프로세스가 죽어도 이어감, HITL이 1급 |
| **컨텍스트 경계** | 이분법 — 전송은 전부 공유, `AgentTool`은 완전 격리 | 범위 지정 — `isolation_scope`, 같은 컨텍스트의 `ctx.run_node`, 확인 요청을 보호하는 Runner 소유 압축 |

**상징적인 예 — `ClassifierNode`.** 1.x라면 "라벨을 반환하는 `LlmAgent` + 그 라벨을 해석하는 코드"로
우회해야 했던 분기가 노드 하나가 되고, 그래프 검증이 **모든 라벨에 간선이 있는지 실행 전에** 확인한다
(→ [결정 모델 분류기](../classifiers/결정모델_분류기_도입현황.md)).

`Workflow` 가이드가 내세우는 세 가지가 이 표의 요약이다.

- 분기와 병렬은 edge 목록에 선언하므로 **사용자 코드의 제어 흐름에 나타나지 않는다.**
- 사람의 입력을 기다리며 멈췄다가 재개하고, 세션 히스토리에서 이미 실행된 것을 재구성해
  **완료된 노드는 다시 실행하지 않는다.**
- `ctx.run_node()`로 런타임에 노드를 만들어 기다릴 수 있다 — **정적 간선 밖에서**.

## 3. 왜 그래프인가

### 3.1 upstream이 밝힌 이유

v2.0.0 릴리스 노트(2026-05-19)는 "비선형·조건·순환 실행 패턴을 오케스트레이션하는 모델 중립 엔진",
"병렬 서브에이전트 워커, 중첩 계층 팀, 동적 스케줄링"을 내세운다. 워크플로 가이드는 위 세 가지
(선언적 분기, 인터럽트·재개, 동적 스케줄링)를 든다.

### 3.2 코드와 이슈 이력에서 읽히는 이유 (해석)

아래는 upstream이 이렇게 말한 것이 아니라, 코드와 이력에서 읽은 해석이다.

1. **재개하려면 "어디까지 했는가"를 가리킬 좌표가 필요한데, 대화 루프에는 좌표가 없다.** 가장
   근본적인 이유라고 본다. 1.x 이벤트는 "누가 무엇을 말했나"만 기록해서, 서브에이전트가 낸 장기
   실행 호출의 응답이 엉뚱한 에이전트로 갈 수 있었다 — `ResumabilityConfig` 가이드가 이 실패를 직접
   설명한다. 그래프에서는 노드 경로가 그대로 주소다. `node_info.path`, 체크포인트 이벤트, "완료된
   노드는 다시 실행하지 않는다", 중단 봉인이 모두 이 좌표를 전제로 한다. **ADK에서 그래프는 문법이기
   이전에 durable execution을 위한 주소 체계다.**
   - 단, **정적 그래프가 durable execution의 필요조건은 아니다.** `pi-durable`은 소유 트리로 묶인
     태스크("매 단계 체크포인트를 저장하는 상태 기계")로, Claude Code의 dynamic workflow는 저장된 에이전트
     결과의 결정적 재생으로 같은 성질을 얻는다. 필요한 것은 **주소 지정 가능한 작업 단위와 원자적
     커밋**이고, 정적 그래프는 그것을 얻는 한 방법이다 — ADK는 그 방법을 택했다.
2. **1.x에는 중간 지대가 비어 있었다.** LLM 라우팅과 고정 합성 사이를 메울 수단이 없어, 진짜 그래프가
   필요하면 `LangGraphAgent`로 외부 프레임워크를 감쌌다. 2.x는 그 수요를 네이티브로 흡수했다.
3. **비용과 지연.** 결정적으로 처리할 수 있는 판단을 LLM 턴에 맡기면 느리고 비싸다. 함수 노드와
   분류기 노드가 그 판단을 가져간다. 메인테이너가 "턴마다 분류하는 게 시간을 아끼는지 측정하겠다"고
   한 것(`#7235`)도 같은 축이다.
4. **검증과 평가.** 그래프는 실행 전에 검증할 수 있고 노드 단위로 평가할 수 있다. 2.14.0에서
   `AgentEvaluator`가 `BaseNode`를 받게 된 것이 그 결과다.
5. 업계 흐름(그래프 기반 오케스트레이션의 확산)과도 맞물린다. 이것은 맥락이지 ADK가 명시한 이유가 아니다.

## 4. 대가

- **실행 저널의 의미론은 맞추기 어렵다.** `#6497` "2.5.0 회귀: 워크플로 replay가 이전 invocation
  이벤트를 섞음", `#7027` "2.8.0: replay 중 HITL 반복 교착", 커밋 `8a43244` "resume 라우팅 결정을
  중앙화하고 서브브랜치/콜백/중단 라우팅 수정".
- **이벤트 모델이 무거워졌다.** 성능 작업이 이어진다 — 2.13.0 "실행 턴 최대 8배 단축", 2.14.0
  "30노드 워크플로 200턴 23% 단축, 피크 메모리 9% 감소".
- **개념 수가 늘었다.** 노드·엣지·조인·트리거·모드·스코프·인터럽트.

반대로 **`LlmAgent` 하나 + 툴** 구성이었다면 체감 차이는 작다. 그래프는 필요할 때 쓰는 층이고 LLM
루프는 그대로이기 때문이다. 마이그레이션 비용은 대부분 주변부(Enum 툴 인자, 세션 저장 포맷, 기능
게이팅, 프로세서 주입 위치)에서 나온다 — [문서 격차 점검](../migration/문서격차점검_v1.26.0_v2.14.0.md) §0.

  `LangGraphAgent` 존속, `flows/llm_flows` 프로세서 구성.
- 공식 근거: v2.0.0 릴리스 노트, `docs/guides/workflow/workflow`·`docs/guides/workflow/graph`·
  `docs/guides/apps/resumability`의 도입부.
- **읽지 않은 것**: 노드 런타임 내부(`_node_runner`, `_dynamic_node_scheduler`, `_node_state`),
  그래프 검증 10규칙 각각, v2.0.0b* 프리릴리스 노트.
