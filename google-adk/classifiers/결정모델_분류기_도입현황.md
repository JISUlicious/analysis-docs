# 결정 모델(decision model) 분류기 도입 현황 — Decisions API · SystemOne API

> 대상: ADK Python **v2.14.0** (`google/adk-python`, `main` @ `1cb926d`, 2026-11-07 공개)
> 코드: `src/google/adk/labs/classifiers/`, `src/google/adk/integrations/typesafe/`, `src/google/adk/integrations/openai/`
> 조사: 2026-11-09. 최신 `main` 클론의 소스·테스트·가이드 직접 확인 + GitHub API로 릴리스/PR/이슈 대조.
> 비교 대상: `google/adk-java` (`main`, 2026-11-08), `google/adk-go`, `google/adk-docs`.

---

## 0. 한 줄 요약

**"decisions API"와 "systemone API"는 ADK가 만든 API가 아니다.** 각각 OpenAI와 TypeSafe가 제공하는
**결정 모델(decision model) 엔드포인트**이고, ADK는 이 둘을 `BaseClassifier`라는 **벤더 중립 인터페이스의
어댑터**로 감싸 넣었다. 인터페이스·구현·테스트는 충실하지만(테스트 2,578줄), 2026-11-09 현재
**experimental 등급 · ADK 내부 미사용 · 공식 문서 사이트 미반영 · 구글 자체 결정 모델 어댑터 없음**이라
"시험 적용 가능, 프로덕션 기본 경로 아님" 단계다.

---

## 1. 결정 모델이란, 그리고 소유권 정리

LLM은 "이 티켓은 어느 팀이 처리해야 하나", "이 툴 호출이 데이터를 지우나" 같은 **선택지가 정해진 작은 판단**도
텍스트를 생성해서 answer한다. 결정 모델은 텍스트를 생성하지 않고 **가능한 답 위의 캘리브레이션된 확률 분포**를
단일 forward pass로 돌려주므로 모델 턴보다 빠르다 (`docs/guides/integrations/typesafe/typesafe_classifier/index.md`).

| 이름 | 소유자 | 실체 |
|---|---|---|
| **SystemOne API** (`/v1/systemone`) | TypeSafe (외부 벤더) | Jev 결정 모델의 HTTP 엔드포인트 |
| **Decisions API** (`/v1/decisions`) | OpenAI (외부 벤더) | Decisions 엔드포인트, 현재 `gpt-6-luna` 전용 |
| `BaseClassifier` / `ClassifierNode` | **ADK** | 위 둘과 LLM을 같은 질문 타입으로 추상화한 계층 |

→ ADK 쪽의 질문은 "이 외부 API들을 어떤 추상화로 받아들였고, 어디까지 들어왔는가"다.

## 2. 공통층 — `google.adk.labs.classifiers`

`src/google/adk/labs/classifiers/` (5파일), `labs/README.md`에 **"실험적이며 예고 없이 변경·삭제될 수 있음,
프로덕션 의존 금지"** 경고가 붙어 있는 영역이다.

| 구성 | 내용 |
|---|---|
| `BaseClassifier` | `async classify(*, input, questions) -> ClassifierResponse`. 텍스트 생성·스트리밍·툴 호출 없음. **상태 비저장** — 이전 턴 문맥은 호출자가 input에 넣어야 한다 |
| 질문 타입 | `Choice`(N개 라벨 중 하나) · `Binary`(참일 확률) · `Score`(0부터 시작하는 순서형 등급) |
| 답 타입 | `ChoiceAnswer`(`choice` + 라벨별 `probabilities`, 합 1) · `BinaryAnswer`(`probability`) · `ScoreAnswer`(기대 등급 + 등급별 확률) · **`RefusalAnswer`** |
| 응답 | `ClassifierResponse(answers: dict[str, Answer], model_version)` — 질문 이름을 키로 되돌려준다 |
| `ClassifierNode` | ADK 2.x 워크플로 라우팅 노드. `Choice`는 라벨, `Binary`는 `threshold`(기본 0.5) 기준 `True`/`False`가 경로. 출력은 **입력 그대로**라 라우팅된 노드가 분류기가 본 것을 받는다. 그래프 검증이 "모든 경로가 가능한 답인지, 모든 답에 간선이 있는지"를 확인(`DEFAULT_ROUTE`/무라우팅 간선이 나머지를 받을 때는 예외) |
| `LlmClassifier` | 같은 질문을 아무 `BaseLlm`으로 답하게 하는 구현. 추가 의존성·API 키 불필요 |

**등급**: `features/_feature_registry.py`에 `FeatureName.CLASSIFIER: FeatureConfig(FeatureStage.EXPERIMENTAL,
default_on=True)` — 기본 켜져 있지만 쓰면 experimental 경고가 로그에 남는다.

**설계 디테일 둘**

- `RefusalAnswer`는 **질문 단위**다. 한 호출의 일부 질문만 거부되고 나머지는 답을 받을 수 있어, 호출 전체를
  실패시키지 않는다(`d45df6a`, 2026-10-29).
- `BaseClassifier.__pydantic_init_subclass__`가 서브클래스의 `classify`를 감싸 **클라이언트 라벨 컨텍스트**를
  씌운다(`7bfe227`, 2026-11-03). 분류기가 보낸 요청이 벤더 쪽에서 구분된다. eval 중처럼 외부 라벨이 이미
  설정돼 있으면 그것을 유지한다.

## 3. 두 어댑터 비교

| | **SystemOne** (TypeSafe Jev) | **Decisions** (OpenAI) |
|---|---|---|
| 클래스 | `integrations.typesafe.TypesafeClassifier` | `integrations.openai.OpenAIDecisionsClassifier` |
| 파일 | `_typesafe_classifier.py` (328줄) | `_openai_decisions_classifier.py` (397줄) |
| 경로 | `POST {base}/v1/systemone`, 기본 `https://api.typesafe.ai` | `POST {base_url}/decisions` → 실질 `/v1/decisions` |
| 인증 | `TYPESAFE_API_KEY` / `TYPESAFE_BASE_URL`, Bearer | `OPENAI_API_KEY` / `OPENAI_BASE_URL`. `api_key`에 **콜러블**(sync/async)을 줄 수 있어 만료 키 대응 |
| 의존성 | **없음** — `httpx` + `tenacity`로 직접 호출 (ADK가 이미 의존) | `pip install "google-adk[openai]"` → `openai>=2.20,<3` |
| 모델 | `jev-latest` 또는 핀(`jev-1.13`) | `gpt-6-luna` — **현재 Decisions API가 지원하는 유일 모델** |
| `Binary` 매핑 | Jev의 `noul` 질문 | OpenAI `predicate` (criteria는 instructions 끝에 합침) |
| 재시도 | 429/529 + 타임아웃/네트워크/프로토콜 오류, `max_attempts=3`(기본), 지수 지터 0.5~8s | openai 클라이언트 자체 재시도 |
| 타임아웃 | 기본 30초 (`http_client` 지정 시 그쪽 기본) | 30초 — **패키지 기본 10분 대신** 턴 경로용으로 낮춤 |
| 호출 상한 | 문서화된 상한 없음 | 1호출 최대 **400 질문**, `Choice` **255 라벨**, `Score` **10 레벨** |
| 구현 메모 | 호출마다 클라이언트를 열고 닫음(`http_client` 미지정 시) | openai 패키지에 Decisions 타입 리소스가 없어 **generic `client.post(_PATH, cast_to=object)`**. `api_key`/`base_url`이 바뀌지 않는 한 만든 클라이언트를 재사용 |

**응답 검증이 엄격하다** (두 어댑터 공통 성향)

- 확률 합·범위 검사, 캘리브레이션 값의 라운딩 오차는 `1e-6`까지 허용 후 클램프.
- OpenAI 쪽은 **불리언 `true`와 문자열 `"true"`를 다른 선택지로 취급**하고, 파이썬에서 `True`가 `int 1`로
  통과하는 것까지 막는 타입 일치 검사를 한다.
- 질문 이름을 echo하지 않거나 중복 답을 주면 `ValueError`. 모델이 라벨 밖의 값을 고르면 거부.

**테스트 분량** — `tests/unittests/integrations/openai/test_openai_decisions_classifier.py` 896줄,
`tests/unittests/integrations/typesafe/test_typesafe_classifier.py` 596줄, 공통층 1,060줄(= 총 2,578줄).
모두 mock 트랜스포트 기반으로 네트워크 없이 돈다.

## 5. 도입 "깊이"를 가르는 네 가지 사실

1. **ADK 자체가 아직 쓰지 않는다.** `src/` 전체에서 `labs.classifiers`를 소비하는 코드는 패키지 자신과 두
   어댑터뿐이다. 사용처는 샘플 두 개 — `contributing/samples/workflows/classifier_node`(티켓을 `ClassifierNode`
   둘로 연쇄 라우팅), `contributing/samples/hitl/classifier_tool_gate`(분류기가 위험하다고 판단한 툴 호출을
   막거나 사용자 확인을 요구). 두 샘플 모두 기본값은 `LlmClassifier(model="gemini-3.5-flash")`다.
2. **커뮤니티 PR은 닫고 내부에서 재설계했다.** `#7235`(+1,441/−30, 21파일, 2026-09-22 제출 → 10-22 닫힘)는
   `TypesafeClassifierTool` 같은 **벤더 전용** 설계였다. 닫는 코멘트가 설계 근거를 남겼다 — 다른 결정 모델
   (OpenAI Decisions API, **DecisionGemma**)도 같은 종류의 타입 질문을 받으므로 provider-agnostic 인터페이스를
   먼저 넣고 Jev를 그 첫 어댑터로 했다는 것. 같은 코멘트에서 **모델 라우터 콜백은 "턴마다 분류하는 것이 시간을
   아끼는지 먼저 측정한 뒤"로 보류**한다고 밝혔다.
3. **`DecisionGemma`는 코드·문서에 없다.** adk-python과 google 조직 코드 검색 모두 0건. 위 코멘트의 언급이
   유일한 흔적이라 **구글 자체 결정 모델 어댑터는 예고 수준**이다.
4. **공식 문서 사이트에 개념 문서가 없다.** 저장소 안 unit guide는 4개
   (`docs/guides/labs/classifiers/{classifier_node,llm_classifier}`, `docs/guides/integrations/{typesafe,openai}/…`)로
   충실하지만, `google/adk-docs`에는 자동 생성 API 레퍼런스(`genindex.html`)만 `labs.classifiers.ClassifierNode`·
   `integrations.typesafe.TypesafeClassifier`를 언급하고, `docs/agents/routing.md`는 여전히 "라우터 함수가 가벼운
   분류기 모델을 호출할 수 있다" 수준에 머물러 있다.

**세 번째 벤더 요청은 코드 없이 닫혔다.** `#7742`(2026-10-26 → 10-28 "completed")는 nace.ai Drex가 같은 프로토콜을
쓴다는 관찰에서 출발해 — `TypesafeClassifier(model='drex-max', base_url='https://console.nace.ai')`로 텍스트 질문은
이미 동작한다 — 이미지 `Part`를 보낼 수 있는 `integrations/nace/DrexClassifier`를 요청했다. 하지만 트리에 `nace`
패키지도 `drex` 언급도 없다. 즉 **이미지 입력 제약은 그대로**다.

## 7. 한계와 운영 주의 (가이드 명시 + 코드 확인)

- **텍스트/JSON 입력만.** 이미지 등 non-text `Part`가 섞인 `types.Content`는 `ValueError`. OpenAI Decisions API
  자체는 이미지와 툴 호출이 섞인 대화 이력도 받지만 **어댑터가 아직 보내지 않는다**.
- **`instructions` 필수.** 두 벤더 어댑터 모두 질문마다 요구한다. `LlmClassifier`만 선택적.
- **외부 전송.** 매 `classify` 호출이 입력과 질문을 벤더 서버로 보낸다. 데이터가 환경을 떠나도 되는지 먼저 확인할 것.
- **임계값은 평가로.** 확률이 캘리브레이션돼 있어도 적절한 임계값은 질문과 "틀린 답의 비용"에 달려 있다.
- **experimental.** 인터페이스가 릴리스 사이에 바뀔 수 있고, 쓰면 `CLASSIFIER` 기능 경고가 로그에 남는다.
- **거부 처리.** `.choice`/`.probability`/`.score`를 읽기 전에 `RefusalAnswer` 여부를 확인해야 한다.
- **OpenAI 상한은 위임.** 400질문 초과를 어댑터가 막지 않고 OpenAI가 `BadRequestError`로 거절하게 둔다
  (상한이 올라간 전례가 있어서).

## 8. 지금 적용한다면

**권고 경로 — 인터페이스만 먼저 채택한다.**

`ClassifierNode`나 툴 게이트 콜백을 `LlmClassifier`(이미 쓰는 Gemini)로 작성해 두면 추가 키·의존성 없이 돌아가고,
나중에 `TypesafeClassifier`/`OpenAIDecisionsClassifier`로 교체할 때 **그래프 코드는 바뀌지 않는다**. 가이드와
샘플이 모두 이 전환을 전제로 쓰여 있다.

반대로 벤더 어댑터를 지금 프로덕션 경로에 넣는 것은 이르다 — ① experimental 인터페이스 ② ADK 내부 미사용(실사용
피드백이 아직 안 쌓임) ③ 공식 문서 부재 ④ Decisions 쪽은 `gpt-6-luna` 단일 모델 의존.

**측정 없이 결정 모델로 갈아타지 말 것.** 메인테이너 자신이 "턴마다 분류하는 게 시간을 아끼는지 측정하겠다"며
모델 라우터를 보류했다. 분류기 호출도 외부 왕복이므로, LLM 한 턴을 줄이는 이득이 왕복 비용을 넘는지는 워크로드에
따라 다르다.

## 9. 조사 방법과 근거 범위

- `main` @ `1cb926d`(v2.14.0) 클론에서 소스 5파일 + 어댑터 2파일 + 가이드 4개 + 샘플 2개 + `pyproject.toml`
  + `features/_feature_registry.py`를 직접 읽었다.
- 커밋 날짜·릴리스 귀속은 GitHub API(`releases/tags/*` 본문, `commits/{sha}`)로 확인했다. 분류기 기능 커밋
  `773418f`·`ddf8c55`·`aa98d18`는 `commits/{sha}/pulls`가 빈 배열 — PR 없이 들어온 내부 커밋이다(→
  [릴리스·개발 운영 현황](../releases/v2.14.0_릴리스_개발운영_현황.md)).
- `#7235`·`#7742`는 본문과 코멘트 전문을 읽었다. **인용한 설계 의도는 메인테이너 코멘트가 근거이고, 로드맵
  문서가 아니다** — `DecisionGemma`와 모델 라우터는 코드로 확인되지 않는다.
- 벤더 API 자체(TypeSafe `/v1/systemone`, OpenAI `/v1/decisions`)는 **ADK 어댑터 코드와 가이드를 통해서만**
  확인했다. 벤더 공식 문서는 대조하지 않았으므로, 상한·모델명·필드는 "ADK가 그렇게 구현했다"까지가 근거다.
