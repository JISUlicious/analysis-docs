# 한 MCP 서버에 여러 분야 도구가 많을 때의 관리 가이드

> **문제**: 서로 다른 분야의 도구가 한 서버에 쌓이면 무엇이 나빠지고, 어떻게 관리하나.
> **검증**: 도구 수에 따른 선언 크기·라우터 패턴·런타임 변경을 SDK 1.29/2.0으로 실측.
> 연관: [내부구조 가이드](MCP_프로젝트_내부구조_가이드.md) · [다중서버 구성](MCP_다중서버_단일프로젝트_구성.md)

---

## 1. 비용의 실체 (실측)

도구 선언은 **매 LLM 스텝마다 프롬프트에 통째로 실린다.** 도구 수에 정확히 비례한다:

| 도구 수 | 선언 크기 | 대략 토큰 | 도구당 |
|---|---|---|---|
| 5 | 2,332자 | ~666 | 466자 |
| 20 | 9,348자 | ~2,671 | 467자 |
| 50 | 23,400자 | ~6,686 | 468자 |
| **100** | **46,820자** | **~13,377** | 468자 |

100개면 **매 호출마다 1.3만 토큰**이 도구 목록으로만 나간다. 게다가 도구가 많아질수록
모델의 선택 정확도가 떨어지는 것은 널리 관찰되는 현상이다(본 문서에서 측정한 것은
토큰 비용까지다).

**선언 크기의 내역** (파라미터 3개 도구 1개 기준):

| 구성 | 장황한 description | 간결한 description |
|---|---|---|
| `inputSchema` | 262자 (49%) | 262자 (74%) |
| `description` | 212자 (40%) | 36자 (10%) |
| `name` 외 | 57자 | 57자 |
| **합계** | **531자** | **355자 (−33%)** |

→ description만 다듬어도 **1/3 절감**. 그 다음 지배 요인은 inputSchema(파라미터 수).

## 2. 1순위 해법 — 서버를 나눈다

**분야가 다르면 서버를 나누는 것이 가장 효과적이다.** 이미 갖춘 구조에서는
`servers/<domain>/` 디렉터리 추가만으로 URL이 분리되고, 사용자는 **필요한 분야만 등록**한다.

```
단일 서버 100개 도구  → 매 스텝 13,377 토큰 (전부 노출)
분야별 5개 서버 × 20개 → 사용자가 2개 서버만 등록 시 5,342 토큰 (60% 절감)
```

부수 효과: 소유권 경계·인증·DB allowlist가 함께 정렬된다(내부구조 가이드 §1).
**아래 기법들은 "그럼에도 한 서버에 많아야 할 때"의 차선책이다.**

## 3. 한 서버 안에서의 관리 기법

### 3-1. 소비자 측 필터 (호스트가 고른다)

ADK `McpToolset(tool_filter=...)`는 **리스트 또는 `ToolPredicate`(콜러블)** 을 받는다
(`base_toolset.py: _is_tool_selected` 확인). 콜러블이면 `readonly_context`를 받으므로
**invocation 컨텍스트에 따라 동적 선별**이 가능하다:

```python
def by_domain(tool, ctx):                      # 세션 상태·에이전트별로 노출 조절
    return tool.name.startswith(ctx.state.get("active_domain", ""))

McpToolset(connection_params=..., tool_filter=by_domain)
```

장점: 서버 수정 없이 호스트가 통제. 한계: **서버는 여전히 전부 노출**하므로 다른
호스트에는 효과 없음.

### 3-2. 서버 측 동적 노출 (서버가 고른다)

런타임 도구 추가/제거가 **실제로 동작한다**(실측: 3개 → 추가 후 4개, `remove_tool` API 존재).
모드·권한·플랜에 따라 노출 집합을 바꾸고 `notifications/tools/list_changed`로 알린다.

```python
srv.add_tool(fn)      # 런타임 추가
srv.remove_tool(name) # 런타임 제거 → list_changed 통지
```

주의: 2026-07-28 스펙은 목록이 **연결별로 달라지는 것을 금지**하되 **자격증명별 차이는
허용**한다. 즉 "이 토큰에는 이 도구들"은 정당하지만, 같은 자격증명에 대해 연결마다
다른 목록을 주면 안 된다.

### 3-3. 라우터(메타도구) 패턴 — 최후의 수단

도구 2개(`list_capabilities` + `invoke`)만 노출하고 실제 능력은 런타임에 발견시킨다:

```
100개 직접 노출 : ~13,377 토큰 (매 스텝)
라우터 2개      :    ~175 토큰 (매 스텝)   ← 98.7% 절감 (실측)
```

**대가가 크다**:
- 모델이 스키마를 모른 채 `invoke(capability, args)`를 호출 → **인자 오류율 상승**
- `outputSchema`·`inputSchema` 표준 검증을 **잃는다** (SDK 자동 검증 무력화)
- 발견을 위한 **왕복 1회 추가** (지연·토큰)
- 호스트 UI가 도구 목록을 보여주지 못함

→ **도구가 수백 개이고 대부분이 한 대화에서 미사용일 때만** 정당화된다. 수십 개
수준이면 서버 분리(§2)가 거의 항상 낫다.

### 3-4. 네이밍 규약 — 표준에 카테고리 필드가 없다

실측: `Tool`에도 `ToolAnnotations`에도 **category/group 필드는 없다**
(`['name','title','description','inputSchema','outputSchema','icons','annotations','execution','_meta']`).
따라서 그룹핑은 **이름 규약**으로 한다.

```
<domain>_<verb>_<object>     예: sales_query_orders, hr_get_headcount
```

> ⚠️ 앞선 [내부구조 가이드](MCP_프로젝트_내부구조_가이드.md) §2-4에서 "도구 이름에
> 접두사를 붙이지 말라"고 한 것은 **서버가 분야별로 분리된 경우**다. 반대로 **한 서버에
> 여러 분야가 섞이면 접두사가 필요하다** — 모델이 분야를 구분할 단서가 이름뿐이기 때문.

부가 분류 메타데이터가 필요하면 `_meta`에 넣는다(표준 확장 자리). 단, 모델이 읽는 것은
name·description이므로 **분류는 이름에 드러나야 실효가 있다**.

### 3-5. description 다이어트 (가장 싼 개선)

- **한 문장 + 사용 시점**: "Query sales orders. Use when the user asks for concrete rows."
- 파라미터 설명은 스키마에 있으니 description에서 **반복 금지**
- 예시·주의사항 장황하게 넣지 않기 (모델은 이미 스키마를 본다)
- 측정: 531자 → 355자 (**−33%**), 100개 서버면 ~4,400 토큰 절약

### 3-6. inputSchema 절제

간결한 description 기준으로 **선언의 74%가 inputSchema**다. 파라미터를 줄이는 것이
그 다음 레버:
- 선택 파라미터를 남발하지 말고 기본값으로 흡수
- 유사 도구 3개를 파라미터 1개(enum)로 통합할 수 있는지 검토 —
  단, enum 통합은 모델의 선택 부담을 도구 이름에서 인자로 옮길 뿐이니 **의미가 정말
  같은 경우에만**

## 4. 결정 기준

| 상황 | 권장 |
|---|---|
| 분야가 명확히 갈리고 사용자도 분야별로 쓴다 | **서버 분리** (§2) — 1순위 |
| 서버는 나눌 수 없고(단일 URL 요구) 도구 수십 개 | 네이밍 규약 + description 다이어트 (§3-4/3-5) + 호스트 tool_filter (§3-1) |
| 권한·플랜에 따라 노출이 달라져야 함 | 서버 측 동적 노출 (§3-2) |
| 도구 수백 개, 한 대화에서 대부분 미사용 | 라우터 패턴 (§3-3) — 대가 감수 |

## 5. 안티패턴

| 안티패턴 | 문제 |
|---|---|
| 분야 무관 도구를 한 서버에 계속 추가 | 매 스텝 토큰 선형 증가 + 선택 정확도 하락 |
| description에 사용법을 문단으로 서술 | 토큰의 40%를 차지, 정작 모델은 요점만 필요 |
| 접두사 없이 `query`, `get`, `list` 같은 범용 이름 | 다분야 혼재 시 모델이 분야를 구분 못 함 |
| 라우터 패턴을 도구 20개에 적용 | 스키마 검증·UI 노출을 잃고 얻는 게 적음 |
| 같은 자격증명인데 연결마다 다른 목록 반환 | 스펙 위반 (연결별 가변 금지) |
