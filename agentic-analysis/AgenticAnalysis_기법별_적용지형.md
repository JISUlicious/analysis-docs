## 1. 결론 먼저

**한 문장**: 에이전트는 **수치 계산의 주체가 아니라 분석의 오케스트레이터**로 쓸 때 작동한다.
조사한 거의 모든 성공 사례가 계산·판정을 코드/통계 기법에 맡기고 에이전트에는 **문제 구성 ·
도구 선택 · 코드 작성 · 결과 해석 · 서술**을 맡긴 구조였다.

이 결론을 지지하는 근거 네 가지:

1. **실무형 다단계 분석의 현재 수준은 낮다.** Adyen 실제 운영 업무에서 뽑은 DABStep
   450+ 태스크에서 최고 추론 에이전트가 **16%**, Hard 태스크는 **14.55%** **[논문]**.
   단발 질의가 아니라 여러 소스를 교차 참조하는 실무 분석은 아직 자동화 수준이 아니다.

2. **통계의 약점이 "방법 선택"이 아니라 "적용 가능성 판단"에 있다.** StatQA(11,623문항)에서
   GPT-4o 최고 **64.83%**. 결정적인 것은 오류의 **성격**이다 — **LLM은 적용성(applicability)
   오류**를, **사람은 기법 혼동(task confusion) 오류**를 낸다 **[논문]**. 즉 LLM은 어떤 검정을
   쓸지는 알지만 **그 검정의 전제가 이 데이터에서 성립하는지를 못 본다.**
   ⚠️ *SECOM 실행 검증에서 현재 코딩 에이전트는 기본 보정·전제 처리를 스스로 했다 (§3-3 주석, §8).*

3. **수치 태스크에서 고전 기법이 여전히 이긴다.** 시계열 이상탐지 예측정비 실험에서
   전통 TSAD 기법이 효과·런타임·고장유형 예측의 트레이드오프에서 최선이고 **사전학습
   LLM은 통계적으로 열위** **[논문]**. 시계열 추론 자체가 약점으로 보고된다 **[논문]**.

4. **에이전트는 실험 피드백에 둔감하다 — 가장 강한 부정 결과.** 베이지안 최적화 평가에서
   **실제 결과를 무작위로 섞은 라벨로 바꿔도 성능이 변하지 않았다** **[논문]**.
   적응적 최적화의 기본 요건이 없다는 뜻이고, 고전 기법(linear bandit·GP)이 전 도메인에서
   일관되게 앞섰다.

**성공 패턴의 정본은 Argos다** **[논문][저장소]**: LLM이 **런타임 탐지를 하지 않는다.**
학습 단계에서 **이상탐지 규칙을 생성·검증·수리**하고, 런타임에는 그 규칙을 고전 규칙
엔진이 실행한다. 결과는 공개 데이터셋 F1 **+9.5p**, 내부 데이터셋 **+28.3p** 개선.
→ **"LLM을 추론 시점이 아니라 규칙 생성 시점에 쓴다"** 가 일반화 가능한 원칙이다. **[해석]**

난이도가 다른 것도 있지만, **에이전트의 병목이 통계 지식이 아니라 다단계 실행·교차 참조·
정확한 결과 보고**에 있음을 시사한다. **[해석]**

### 3-1. 한눈 매트릭스

적합도는 **현재 수준에서 에이전트에 맡겼을 때의 신뢰도**다. **[해석]** (근거는 각 절)

| 기법군 | 적합도 | 무엇을 맡기나 | 무엇을 맡기면 안 되나 |
|---|:---:|---|---|
| 데이터 프로파일링·품질 점검 | **높음** | 결측/타입/분포/중복 스캔, 규칙 대조 | 품질 기준 자체의 결정 |
| 기술통계·EDA | **높음** | 요약·교차표·분포 탐색, 코드 작성 | "흥미로운 발견" 단독 판정 |
| 시각화·리포팅 | **높음** | 차트 생성, 서술, 문서 조립 | — |

| 가설검정·통계 추론 | **중** | 기법 **선택** | **전제 검증(적용성)** — LLM의 고유 약점 ⚠️ *§8에서 기본 처리는 에이전트가 스스로 함. 다단계 보정 일관성은 여전히 구멍* |
| 상관·회귀·다변량 | 중 | 모델 적합 코드 | 다중비교·교란 통제 판단 |
| 이상탐지 (시계열) | **중하** | **규칙/특징 생성**(Argos) | **런타임 탐지 판정** |
| 시계열 예측 | **낮음** | 파이프라인 조립 | 시간 의존성 모델링 자체 |
| 분류/예측 모델링·AutoML | 중 | 파이프라인·특징공학 반복 | 누수(leakage)·검증 설계 |

| **인과추론** | **낮음** | 결과의 **해석·설명** | **인과 구조 판정** |
| **실험설계(DoE)·최적화** | **낮음** | 사전지식 제공(LLMNN) | **적응적 탐색 루프** — 피드백 둔감 |

| 신뢰성·생존분석 | 미조사 | — | — |

### 3-2. 강한 쪽 — 준비·탐색·서술

**데이터 품질·프로파일링**: 규칙 대조형 작업이라 코드로 결정화하기 쉽고 검증도 기계적이다.
[nimrodfisher/data-analytics-skills](https://github.com/nimrodfisher/data-analytics-skills)가
이 영역에 5개 스킬을 두고 있다(programmatic EDA, data quality audit, query validation,
schema mapper, metric reconciliation) **[저장소]**. **[해석]** 이 영역이 스킬로 만들기 가장
쉬운 이유는 산출물이 **검증 가능한 형태**(통과/실패 목록)이기 때문이다.

**EDA·시각화·리포팅**: 에이전트의 서술 능력이 그대로 값이 되는 영역. 다만 InsightBench가
드러내듯 **"무엇이 인사이트인가"의 판정은 별개 문제**다 — 그래서 벤치마크가 데이터에
인사이트를 **심어 놓고** LLM-as-a-judge로 매칭한다 **[논문]**.

> ⚠️ 여기가 §5(검증 격차)와 만나는 지점이다. 그럴듯한 서술을 잘 만드는 능력은
> **틀린 결론도 잘 포장한다**. 강점과 위험이 같은 능력에서 나온다. **[해석]**

### 3-3. 중간 — 통계 추론의 "적용성" 구멍

StatQA의 발견이 이 영역 설계를 결정한다 **[논문]**:

```
LLM  : 기법 종류는 안다  →  전제·적용 가능성 판단에서 틀린다 (applicability error)
사람 : 전제는 잘 본다    →  어떤 기법인지 혼동한다        (task confusion error)
```

**상보적이다.** 그래서 설계는 **에이전트가 기법 후보를 제안하고, 전제 검증은 코드로 강제**
하는 쪽이 된다 — 정규성·등분산·독립성·표본크기 검정을 `scripts/`의 결정적 체크로 내리고
통과 못 하면 진행을 막는다. **[해석]**

> ⚠️ **실행 검증에서 순진한 형태로는 기각됐다** ([SECOM 검증 §4-3](secom-verify/README.md)).
> Codex(`gpt-5.6-terra`)는 요청 없이 상수 센서 제외·BH-FDR·시간 구간 보정 회귀를 했고, 무작위
> 교차검증과 시간 외삽을 대조해 시간 누수까지 지적했다 (H2 기각, 0/3). StatQA(GPT-4o, 2024)를
> 현재 프런티어 코딩 에이전트에 그대로 옮기면 과장이다. 남은 구멍은 한 층 위에 있었다:
> **다단계 보정의 일관성**(1차 선별은 전체 보정, 시간 보정 단계는 후보만)과 **서술과 구조화 출력의
> 불일치**. 반대로 이 검증 코드를 쓴 Claude는 사실상 상수인 센서에 점근 검정을 적용하는 적용성
> 오류를 실제로 저질렀고, 순열 대조로 잡혔다 ([§3-3](secom-verify/README.md)).

별도 연구에서 6개 LLM이 20개 가설 시나리오의 **검정 선택을 100% 맞혔다**는 보고도 있다
(설명 품질은 편차 큼) **[논문]** — StatQA(11,623문항, 64.83%)와 규모·난이도가 다르므로
**"선택은 되고 적용성은 안 된다"는 구도와 모순되지 않는다.** **[해석]**

### 3-4. 약한 쪽 1 — 시계열

| 근거 | 내용 |
|---|---|
| [Can LLM Coding Agents Reason About Time Series?](https://arxiv.org/pdf/2606.16545) | 예측·이상탐지·패턴인식 전반에서 **고전 통계 기법 대비 열위**. 실패 모드: **시차 의존성 모델링 실패 · 긴 시퀀스 컨텍스트 제약 · 통계 전제 위반 · 문법은 맞지만 의미가 틀린 코드** **[논문]** |
| 예측정비 TSAD 실험 (ACM SIGMOD) | 전통 TSAD가 효과·런타임·고장유형 예측 트레이드오프에서 최선, **사전학습 LLM은 통계적으로 열위** **[논문]** |
| LLM 기반 이상탐지 실측 | GPT-3.5 계열은 **recall 매우 높고 precision 극히 낮음** — 피크를 과다 플래깅해 F1 붕괴 **[논문]** |

**"문법은 맞지만 의미가 틀린 코드"** 가 가장 위험하다. 실행이 되고 숫자가 나오므로
파이프라인이 조용히 잘못된 값을 낸다. **[해석]**

제조 센서 데이터가 정확히 이 영역이다. 논문은 **제조 모니터링 배포 전에 상당한 개선이
필요**하다고 결론 **[논문]**.

### 3-5. 약한 쪽 2 — 실험설계·최적화 (가장 명확한 부정 결과)

[LLMs for Bayesian Optimization in Scientific Domains: Are We There Yet?](https://arxiv.org/abs/2509.21403) **[논문]**:

- 설정: 유전자 섭동·분자 물성 탐색에서 LLM의 in-context 실험설계 능력 평가
- **핵심 결과**: *"실제 결과를 무작위로 치환한 라벨로 바꿔도 성능에 영향이 없다"*
  → **실험 피드백에 완전히 둔감**
- 고전 기법(linear bandit, GP 최적화)이 **전 도메인에서 일관되게 우위**
- 저자 결론: 현재 LLM에는 **진정한 in-context 실험설계 능력이 없다.**
  **"사전지식 기반 추론과 사후분포 갱신 기반 배치 획득을 분리하는 하이브리드"** 권고
- **LLMNN**(LLM-guided Nearest Neighbour): LLM의 사전지식 + 최근접이웃 샘플링 조합으로
  경쟁력 확보 — **LLM은 사전지식 공급원, 탐색 루프는 고전 기법**

> 제조 DoE(공정 조건 최적화)에 그대로 적용되는 결과다. **에이전트에게 "다음 실험 조건을
> 정하라"고 시키면 안 된다.** 요인·수준 후보를 제안하게 하고 설계·해석은 고전 DoE로. **[해석]**

### 3-6. 약한 쪽 3 — 인과추론

RCA 문서 §3-5와 같은 결론 **[해석]**: 조사한 모든 시스템이 **인과 구조 판정을 LLM 밖에**
둔다. CausalTrace(뉴로심볼릭, 제조), Causal-LLM(제약기반 인과발견 + LLM 설명 생성),
인과발견 기반 RCA(반사실 예측) 전부 같은 분업이다 **[논문]**. LLM 역할은 **맥락화·설명·조율**.

상관은 데이터에 항상 있고 변수가 많을수록 더 많다. 에이전트는 이를 인과로 보고하는
경향이 있고, 이것이 §5의 위험과 직결된다.

## 4. 반복되는 설계 원칙

기법이 달라도 성공 구성에서 같은 원칙이 반복된다. **[해석]**

### 원칙 1 — 계산은 코드로, LLM은 오케스트레이션 (Argos 패턴)

[Argos](https://github.com/microsoft/argos) **[저장소]**가 이 원칙의 가장 명확한 구현이다:

```
기존 LLM 이상탐지 :  런타임마다 LLM이 판정        → 비재현적·비쌈·부정확
Argos             :  학습 시 LLM이 "규칙"을 생성  → 런타임엔 고전 규칙 엔진이 실행
                     여러 에이전트가 규칙을 제안·검증·수리·정제 (피드백 루프)
                     결과: F1 공개 데이터 +9.5p, 내부 +28.3p
```

산출물이 **설명 가능하고 재현 가능한 규칙**이라는 점이 핵심이다 — 품질 감사가 필요한
제조 도메인에서 특히 값이 크다. **[해석]**

이 패턴의 일반형: **LLM의 출력은 "답"이 아니라 "답을 내는 절차"여야 한다.**

### 원칙 2 — 데이터를 컨텍스트에 넣지 않는다

OpenRCA 베이스라인은 Python으로 조회·분석하게 하고(*"모델이 추론에 집중하게 하고 대용량
텔레메트리에 확장 가능하게"*), MongoDB 참조 아키텍처는 시계열을 **집계 통계(min/max/avg)로만
반환**한다 **[저장소][문서]**. 정확도와 비용 양쪽에서 이득이다.

### 원칙 3 — 적용성 검증을 에이전트에 맡기지 않는다

StatQA(§3-3)의 직접 함의. 전제 검증은 **결정적 스크립트**로. **[해석]**

### 원칙 4 — 생성과 검증을 다른 주체에 둔다

| 사례 | 분리 방식 |
|---|---|
| Argos | 규칙 제안 에이전트 ↔ 검증·수리 에이전트 |
| OpsHarness | **dual-gate** — 개선 + 비퇴행 둘 다 통과해야 지식 채택 (없으면 약한 모델에서 정확도 붕괴) |
| automotive-skills-suite | **builder 스킬 ↔ reviewer 스킬** 쌍 |
| VerifyMAS | 직접 예측 대신 **가설 수립 → 전체 궤적에 대해 검증** |
| Microsoft ReAct 연구 | 도구 접지로 환각 40%→4%, 오답의 66%가 **"증거 불충분"** |

### 원칙 5 — 적응 루프는 고전 기법에 맡긴다

§3-5의 피드백 둔감 결과. **에이전트를 루프 안의 의사결정자로 두지 말고, 루프 밖의
사전지식 공급자·해석자로 둔다.** **[해석]**

## 5. 관통하는 위험 — 검증 격차

기법과 무관하게 작동하는 실패 모드다. RCA 문서 §6에서 다뤘으나 분석 전반에 해당한다.

[Sound Agentic Science Requires Adversarial Experiments](https://arxiv.org/html/2604.22080v1)
**[논문]**: 동일 NHANES 데이터를 두 에이전트에 **반대 목표**로 주자 —

| | 결과 |
|---|---|
| Agent A | 유의한 음의 상관, **p=0.0006** |
| Agent B | 연관 없음, **p=0.855** |

**양쪽 다 방어 가능한 방법론적 선택을 썼다.**

논문의 진단: 소프트웨어는 코드가 명세에 대해 상시 테스트되지만 데이터 분석 에이전트에는
그런 반증 장치가 없다 — **"verification gap"**. 에이전트는 *데이터가 지지하는 것처럼 보이는
가설을 빠르게 섞을 수* 있지만 경쟁 가설을 배제할 실험을 돌리지 못한다 **[논문]**.

제안: **falsification-first** — 모든 결과에 **결론을 깨려 시도한 흔적**을 함께 싣고,
리뷰어가 에이전트를 반증 시도에 사용한다 **[논문]**.

> 분석 지시는 대부분 방향성을 갖는다("원인을 찾아라", "개선 효과를 확인하라"). 그 방향으로
> 지지 증거를 찾아오는 것이 §3-2에서 본 서술 능력의 이면이다. **[해석]**

> ✅ **실행 검증에서 재현됐다 — 예상과 다른 형태로** ([SECOM 검증 §4-3~4-5](secom-verify/README.md)).
> - 라벨을 섞어 원인이 존재할 수 없는 데이터에서 맨몸 에이전트 **3/3이 원인 센서를 보고**했다.
>   "원인이 없으면 빈 배열"을 프롬프트가 명시적으로 허용했는데도.
> - 보고서 본문은 "확정할 원인은 없다", "FDR 기준을 넘었다"고 신중했다. **`result.json`에는 노이즈
>   센서가 들어갔다** (한 런은 medium 확신도). 후속 시스템이 읽는 것은 구조화 출력이다.
> - 3회 모두 **같은 노이즈 센서**를 골랐다. 고른 센서들은 468개 중 시간 보정 p값 1·2·3위 그대로다.
>   **런 간 일치는 타당성의 증거가 아니다** — 같은 통계는 같은 노이즈 최댓값을 재현한다.
> - 실제 라벨에서는 3회의 1순위 원인이 갈렸고, 각각 방어 가능한 근거가 있었다 — NHANES 사례의 제조
>   실데이터판.

멀티에이전트로 가면 실패 모드가 추가된다 — **Premature Action**(근거 없이 행동),
**Over-Helpfulness**(빠진 항목을 지어서 채움), **Context Pollution**, **Fragile Execution**
4원형과 14종 taxonomy(System Design / Inter-Agent Misalignment / Task Verification
Failures) **[논문]**.

## 6. 제조 도메인 기법 매핑

제조 분석 기법을 §3 지형에 얹으면: **[해석]**

| 제조 기법 | 대응 기법군 | 적합도 | 설계 |
|---|---|:---:|---|
| **SPC / 관리도** | 이상탐지(규칙형) | 중 | **Argos 패턴** — 룰(Western Electric 등)은 코드, 에이전트는 위반 해석·맥락화 |
| **공정능력 Cp/Cpk** | 기술통계 | **높음** | 계산은 결정적 스크립트. 산업 기준 Cpk **1.33 이상 양호 / 6σ는 1.67** **[문서]**. 에이전트는 전제(정규성·안정성) 확인과 해석 |
| **MSA / Gauge R&R** | 분산분석 | 중 | 계산은 AIAG 표준 절차(스크립트). **전제 검증이 핵심이라 §3-3 구멍에 정확히 걸린다** |
| **DoE (공정조건 최적화)** | 실험설계 | **낮음** | §3-5. 에이전트에 조건 선택 금지. 요인·수준 후보 제안 + 해석만 |
| **불량 공통성 분석** (lot/설비/챔버) | 교차표·검정 | 중 | 쿼리는 에이전트, **다중비교 보정은 코드로 강제** (설비 수백 개 = 우연 유의 다발) |
| **파라미터-불량 상관** | 상관·회귀 | 중하 | 상관은 항상 나온다. 인과 판정 금지(§3-6) |
| **웨이퍼맵 패턴 분류** | 이미지 분류 | 낮음 | 전용 모델 영역. 에이전트는 **멀티모달 검색으로 유사 과거 사례 조회**(MongoDB 참조 아키텍처 패턴) |
| **예측정비 / 이상탐지** | 시계열 | **낮음** | §3-4. 전통 TSAD가 우위 |
| **가상계측(VM)** | 회귀·예측 | 낮음 | 전용 모델 영역 |
| **수율 분석 / excursion** | 복합 | 중 | 탐지는 비-에이전트 스트림, 에이전트는 **조사** (참조 아키텍처 §4) |
| **RCA / 8D** | 복합 | 중하 | [RCA 문서](AgenticRCA_연구지형_조사.md) |

**패턴**: 제조 기법 대부분이 **계산 자체는 표준화되어 있고**(AIAG·Western Electric·Cpk 공식)
**전제 판단과 해석이 어렵다.** 이는 §3-3의 LLM 약점과 정확히 겹치므로, **계산을 스크립트로
내리고 전제 체크를 결정적으로 강제하는 구성**이 거의 모든 항목에 공통으로 적용된다. **[해석]**

## 7. Agent Skills 패키징 설계

[3단계 로딩](../agent-skills/Agent_Skills_작성표준.md)에 §4의 원칙을 배치하면: **[해석]**

| 내용 | 배치 | 이유 |
|---|---|---|
| 분석 절차·판단 기준·언제 무엇을 쓰는지 | `SKILL.md` 본문 (L2) | 항상 필요, 500줄 이내 |
| 도메인 정의(공정·설비·계측 의미, 지표 신뢰 조건) | `references/` (L3) | 크고, 필요할 때만 |
| **계산·전제검증·다중비교 보정** | **`scripts/`** (L3) | **원칙 1·3. 실행하면 출력만 토큰을 쓴다** |
| 트리거 조건 | `description` | 제조 용어·파일 확장자·캐주얼 표현 포함 |

**스킬 분할 제안**:

```
생성 스킬 (builder)            검증 스킬 (reviewer)
─────────────────────         ─────────────────────
분석 수행·서술          ↔     전제 검증 · 반증 시도 · 대안 가설 제시
                              → 원칙 4 + falsification-first(§5)를 구조로 강제
```

automotive-skills-suite의 builder/reviewer 쌍이 이 형태이고 **[저장소]**, 같은 저장소의
**"하류 스킬이 상류 스킬의 파일 출력을 소비하는 안정 계약"** 은 분석 파이프라인
(프로파일링 → 탐색 → 검정 → 리포트)에 그대로 적용된다.

**기대치 설정**: DABStep 16%(§2)가 실무 다단계 분석의 현실이다. 스킬의 성공 정의를
**"분석을 자동으로 수행한다"가 아니라 "분석 경로를 좁히고, 계산을 표준화하고, 증거와
반증 시도를 정리한다"** 로 잡는다. **[해석]**

## 8. 실행 검증 — SECOM × Codex

상세: [`secom-verify/README.md`](secom-verify/README.md). UCI SECOM(실제 반도체 공정, 센서 590 ×
1,567건, 불량 104)을 익명화하고, 라벨을 섞어 **원인이 존재할 수 없는 데이터**를 만들었다.
Codex CLI `gpt-5.6-terra`(reasoning high)를 조건당 3회, 가설·채점 기준은 실행 전 해시로 고정.

| 조건 | 결과 |
|---|---|
| A — 실제 라벨, 맨몸 | 3/3 BH-FDR·상수 제외·시간 보정 수행. 1순위 원인이 런마다 갈림 |
| A′ — 섞은 라벨, 맨몸 | **3/3 원인 센서 보고** (1~2개, low~medium). 3회 모두 같은 노이즈 센서 |
| B′ — 섞은 라벨, 스킬 | **3/3 원인 0개**. 시간 1/4.6, 입력 토큰 1/3.5 |

| 이 문서의 주장 | 검증 |
|---|---|
| §5 검증 격차 | ✅ 재현 — 단 서술은 신중하고 구조화 출력에 노이즈가 들어가는 형태 |
| §3-3 적용성 구멍 | ⚠️ 순진한 형태로는 기각 (H2, 0/3). 구멍은 다단계 보정의 일관성으로 이동 |
| §4 원칙 1·4 (코드 계산 + 생성/검증 분리) | ✅ 지지 — 허위 보고 3/3 → 0/3. **비퇴행(실제 신호 보존)은 미검증** |

**이 검증이 조사 문서에 더하는 두 가지** — 문헌 조사로는 나오지 않았다:

1. **서술과 구조화 출력의 불일치.** 에이전트가 보고서에 "원인 없음"을 쓰고 JSON에 후보를 넣는다.
   스킬 설계에서 검토 스크립트(`check_claims.py`)가 **서술이 아니라 구조화 출력을 검사**해야 하는 이유.
2. **런 간 일치의 함정.** 여러 번 돌려 같은 답이 나오는 것은 분산을 줄일 뿐 편향을 없애지 않는다.
   자기일관성(self-consistency) 투표를 분석 검증 수단으로 쓰면 노이즈 최댓값에 확신을 더한다.
